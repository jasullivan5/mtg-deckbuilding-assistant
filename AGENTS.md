# Development instructions

This long-term Commander research project explains why cards matter in context, rather than assigning universal card-strength scores or reproducing popular decks. Build an enjoyable, inspectable research environment while preserving mechanical accuracy and reproducibility. The user directs objectives and major architecture. Implement the assigned scope; do not rebuild the selected Kotlin/JDK 21/Gradle/Argentum foundation or invent a next card/diagnostic phase.

- Two repositories: this application owns discovery, eligibility, assurance and research diagnostics; [our Argentum fork](https://github.com/jasullivan5/argentum-engine) owns native engine/SDK changes. Original upstream is reference only. Engine feature/fix branches and internal PRs use `app-stable`; fork `main` tracks upstream. No upstream PRs without explicit changed user direction; no wholesale modern imports or generic fork-sync on default `app-stable`.
- The application normally uses the clean sibling `../argentum-engine` on our maintained fork's `app-stable`. There is no separate dependency-pin adoption. Engine feature PRs require native and application compatibility checks before acceptance into app-stable. Record the actual engine SHA in builds/results; preserve clean-source/origin safeguards and historical evidence bindings. Keep the normal stable checkout available by isolating engine feature work when needed. See [integration workflow](docs/ENGINE_WORKFLOW.md).
- Ordinary work uses a feature/fix branch in the primary checkout (application base `main`, engine base `app-stable`). Worktrees require a practical simultaneous-isolation need. Reuse clean checkouts; after evidence is retained, check modifications, untracked files, unpushed commits, active processes and references before normal `git worktree remove` without force. Preserve branches; retain ambiguous clones or active validation. Do not reset/clean/delete work to make removal succeed.
- Respect Commander legality and full color identity through `Catalog.eligibility` effective metadata. Raw native helpers are diagnostics. Corrections require reviewed source/physical-identity/snapshot/implementation bindings; preserve original metadata and definition objects. Identity association is observational, not an eligibility or mechanics certificate; version the mapping algorithm when its rules change.
- Separate structural mechanical possibility, objective policy acceptance, engine execution, translation fidelity, independent qualification and strategic desirability. MATCH is conditional potential. Preserve UNKNOWN, unsupported structures and consequential costs/effects, controller/owner/source/zone/target/quantity/timing/branch relationships.
- Extend the existing native walker, reusable facts and predicates. Keep objective policies separate. A retains legacy death/removal projection; B/C compose facts. Prefer generic engine/SDK corrections over card-specific patches. No production card-name exceptions, new Oracle parser, ranking ontology or unrelated dependency upgrades without assignment. UI and local API development must stay within specifically authorized interface scope; the working direction below is not an implementation assignment.
- Source-first requirements and adversarial execution evidence are required at the appropriate scope. Never rewrite frozen expectations to pass a test. Author/agent tests are bounded evidence, not independent certification; independent qualification requires independent source- and revision-bound review. Preserve historical failures, provisional assurance, source/test hashes and concern history; no automatic promotion or resolution from an engine merge alone.
- Run appropriate focused checks; shared extraction/eligibility/policy changes require full application tests and controlled unchanged-pool comparisons. Scale checks to the actual change; report passed, failed and unexecuted results. Do not claim old receipts as new execution or frozen samples as whole-catalog recall.
- Keep source, compact reviewed evidence and real Git history. Ignore nested dependencies, caches/builds, bulk generated JSON, credentials and machine configuration. No force-push over unrelated work or deletion of historical evidence/branches without authorization.

Use `dev`/`dev.ps1`, not root `gradlew test`. Setup: `bash scripts/bootstrap.sh`; focused tests: `./dev test --tests '<class>'`; all application tests: `./dev test`; gates: `bash scripts/verify.sh fast` (use `full` or `catalog` for the broader checks). CLI and platform entry points are in [README](README.md).

## Collaboration and delivery

| Job | Responsibility |
|---|---|
| Product Studio — user and ChatGPT | Research questions, product goals, experience priorities, major architecture/scope, evaluation criteria and the next meaningful capability. ChatGPT challenges assumptions, proposes alternatives and helps bound assignments; the user retains consequential decision authority. |
| Codex Build — focused implementation sessions | Inspect current Git state; implement approved functionality; handle routine technical design, source organization and tests without asking the user to supervise those choices; preserve evidence; deliver small reviewable PRs, runnable demonstrations and clear instructions. Do not silently expand scope or merge without authorization. |
| Prototype Lab — user and ChatGPT | Try actual running functionality, investigate confusing behavior, review useful or misleading results, compare demonstrated and intended capabilities, and recommend accept/revise decisions. Product evaluation does not independently certify card translation accuracy. |

Git remains authoritative for implementation continuity. These jobs do not require permanent separate repository processes or project-management infrastructure.

Prefer small, meaningful end-to-end increments that the user can launch, explore and evaluate. Implementation completion and passing tests do not automatically establish an accepted user experience. A user-facing delivery should ordinarily include:

1. A reproducible, straightforward local launch and a concise explanation of what the user can do now.
2. Two or three guided tasks with real MTG examples (for discovery, inspect Judith, choose an existing objective, and inspect a pathway's prerequisites).
3. At least one meaningful limitation, unknown or negative case, such as unsupported commander construction or unavailable imagery.
4. Relevant tests actually executed, source/revision provenance and outstanding problems; distinguish unexecuted checks and historical receipts.

The user evaluates understandability and usefulness before a substantial user-facing capability is accepted. Backend-only corrections and investigations remain appropriate when they are the cheapest adequate approach. Where practical, expose consequential findings through existing research views, scenario evidence or diagnostics; do not add decorative UI solely to satisfy this process.

## Approved interface direction — M1 awaiting user evaluation

Technology Audit 001 informed the selected working direction: an independent React / TypeScript / Vite research interface in this repository, beginning with a Commander Discovery Explorer. It should support commander selection, selection among existing objectives, genuine discovery execution, identity-verified card imagery, browsable card grids/lists, readable mechanical explanations, inspectable prerequisites/decisions/evidence/limitations and meaningful interactive research visualizations. Make it attractive, responsive, keyboard-accessible and pleasant to explore.

Preserve Kotlin/JDK 21/Gradle, the CLI and headless tests. A narrow application-owned local Kotlin boundary is the leading integration approach; lightweight HTTP is favored. Framework, schema, lifecycle and error handling require bounded implementation and review. Ktor or another framework is neither implemented nor required by this decision. The frontend presents existing native extraction and application decisions; it must not independently reinterpret MTG rules.

The application owns Commander eligibility/discovery integration, objective interpretation, translation assurance, source/identity observations, research presentation, frontend/local API integration and app-stable compatibility. The independent sibling fork owns native card structures, SDK semantics, rules execution, generic mechanical corrections and native regressions. Selective reuse of Argentum presentation components, imagery utilities or icons requires coupling, provenance and licensing review. Do not adopt the complete game client or its hosted gameplay architecture by default. See [architecture](docs/ARCHITECTURE.md#research-interface).

This direction does not authorize hosted accounts, multiplayer, general deck editing, persistent databases, desktop packaging, cloud infrastructure, a comprehensive game client, new mechanical objectives or a replacement rules engine. Such scope needs demonstrated need and appropriate approval. M1 implements the bounded live foundation described in [Explorer M1](docs/EXPLORER_M1.md); subsequent increments require a separate bounded assignment.

## Visualization fidelity

The interface is part of the research system; presentation must preserve the underlying evidence:

- Keep physical card identity/eligibility, native representability, translation fidelity, engine execution, mechanical discovery, objective relevance and contextual deck value separate. A structural `MATCH` is conditional possibility, not guaranteed resolution or an inclusion recommendation. A passed scenario does not independently verify an entire card. Preserve provisional, blocked, unsupported, untested and unknown findings. Do not invent confidence percentages or universal card-quality scores.
- Every consequential chart identifies its measured population, units/counting granularity, commander/objective/filters, dataset and implementation revisions, exclusions/missing values/unknowns, and whether data is observed, historical or illustrative. Distinguish physical cards, faces, actions, pathways, scenarios and tests; identify overlapping categories. No emitted pathway is not proven `NO_MATCH`. Where appropriate, allow drill-down to contributing records and failures.
- Card imagery requires verified physical-card, printing and face identity. Provide a clear fallback for missing or uncertain associations, respect provider terms/attribution/usage restrictions, and never silently substitute approximate art by name.
- Distinguish source-derived expectations, previously recorded execution, freshly executed engine scenarios and mock/illustrative data. Never depict fictional state transitions as observed execution. Explain findings in readable MTG terms with access to native mechanics and supporting evidence.
