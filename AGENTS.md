# Development instructions

This long-term Commander research project prioritizes mechanical accuracy and reproducibility. The user directs objectives and major architecture. Implement the assigned scope; do not rebuild the selected Kotlin/JDK 21/Gradle/Argentum foundation or invent a next card/diagnostic phase.

- Two repositories: this application owns discovery, eligibility, assurance and research diagnostics; [our Argentum fork](https://github.com/jasullivan5/argentum-engine) owns native engine/SDK changes. Original upstream is reference only. Engine feature/fix branches and internal PRs use `app-stable`; fork `main` tracks upstream. No upstream PRs without explicit changed user direction; no wholesale modern imports or generic fork-sync on default `app-stable`.
- Application `main` and its exact `ARGENTUM_COMMIT` authorize dependency adoption. Engine acceptance is a separate review. Preserve exact-revision, clean-checkout and source-origin safeguards. The nested `argentum/` is a pinned dependency, not the ordinary development checkout. See [integration workflow](docs/ENGINE_COUNTER_CORRECTION.md).
- Ordinary work uses a feature/fix branch in the primary checkout (application base `main`, engine base `app-stable`). Worktrees require a practical simultaneous-isolation need. Reuse clean checkouts; after evidence is retained, check modifications, untracked files, unpushed commits, active processes and references before normal `git worktree remove` without force. Preserve branches; retain ambiguous clones or active validation. Do not reset/clean/delete work to make removal succeed.
- Respect Commander legality and full color identity through `Catalog.eligibility` effective metadata. Raw native helpers are diagnostics. Corrections require reviewed source/physical-identity/snapshot/pin bindings; preserve original metadata and definition objects. Identity association is observational, not an eligibility or mechanics certificate; version the mapping algorithm when its rules change.
- Separate structural mechanical possibility, objective policy acceptance, engine execution, translation fidelity, independent qualification and strategic desirability. MATCH is conditional potential. Preserve UNKNOWN, unsupported structures and consequential costs/effects, controller/owner/source/zone/target/quantity/timing/branch relationships.
- Extend the existing native walker, reusable facts and predicates. Keep objective policies separate. A retains legacy death/removal projection; B/C compose facts. Prefer generic engine/SDK corrections over card-specific patches. No production card-name exceptions, new Oracle parser, ranking ontology, UI/database/server or unrelated dependency upgrades without assignment.
- Source-first requirements and adversarial execution evidence are required at the appropriate scope. Never rewrite frozen expectations to pass a test. Author/agent tests are bounded evidence, not independent certification. Preserve historical failures, provisional assurance, source/test hashes and concern history; no automatic promotion or resolution from a pin merge alone.
- Run appropriate focused checks; shared extraction/eligibility/policy changes require full application tests and controlled unchanged-pool comparisons. Scale checks to the actual change; report passed, failed and unexecuted results. Do not claim old receipts as new execution or frozen samples as whole-catalog recall.
- Keep source, compact reviewed evidence and real Git history. Ignore nested dependencies, caches/builds, bulk generated JSON, credentials and machine configuration. No force-push over unrelated work or deletion of historical evidence/branches without authorization.

Use `dev`/`dev.ps1`, not root `gradlew test`. Setup: `bash scripts/bootstrap.sh`; focused tests: `./dev test --tests '<class>'`; all application tests: `./dev test`; gates: `bash scripts/verify.sh fast` (use `full` or `catalog` for the broader checks). CLI and platform entry points are in [README](README.md).

Read [architecture](docs/ARCHITECTURE.md), [authoring](docs/COMMANDER_AUTHORING.md), [assurance](docs/TRANSLATION_RELIABILITY.md) and [recorded verification](HANDOFF_VERIFICATION.md) as needed. Keep detailed guidance there. Project references own long-term vision; this repository owns application implementation; the fork owns engine/SDK detail and native regressions.
